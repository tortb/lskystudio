# Lsky Studio 上传核心逻辑 JS → Rust 迁移 Spec

## 1. 背景与目标

当前上传相关核心逻辑用 Node.js 实现（约 5-6 个文件，单文件约 300 行，部分更短），通过 Tauri sidecar 方式被 Rust 主进程调用。本次迁移目标：将这部分逻辑完全用 Rust 重写，消除 Node.js 运行时依赖。

**收益：**
- 移除 CI/CD workflow 中 Node sidecar 二进制打包步骤（见项目 spec 第 5.1 节），简化全平台构建
- 减少安装包体积、去掉一个独立运行时进程
- 统一技术栈，前端 React 直接通过 Tauri `invoke` 调用 Rust command，调用链更短

## 2. 迁移原则

- **按文件级别迁移，不做整体重写**：每次迁移一个文件对应的功能模块，迁移后立即验证该功能，再进行下一个，避免一次性大改导致问题定位困难
- **先读后写**：迁移前完整阅读对应 JS 文件，列出该文件涉及的所有 Node 特有 API 调用，逐一找到 Rust 对应方案，再动手写代码
- **不逐行翻译，按语义重构**：JS 的 Promise 链、回调风格要按 Rust `async/await` 惯用法重新组织，而不是保留原有控制流结构
- **保留原有对外接口不变**：Tauri command 的名称、参数、返回值结构尽量与迁移前一致，减少前端 React 侧的改动面

## 3. 技术选型对照表

| JS 侧能力 | Rust 对应方案 |
|-----------|---------------|
| HTTP 请求 / multipart 上传 | `reqwest`（启用 `multipart` feature） |
| 异步运行时 | `tokio` |
| JSON 序列化/反序列化 | `serde` + `serde_json` |
| 文件读取（含大文件流式读取） | `tokio::fs`，配合 `tokio_util::io::ReaderStream` 做流式上传 |
| 文件 hash 计算 | `sha2` / `md5` crate（根据兰空图床 API 要求的哈希算法选择） |
| 并发上传队列控制 | `tokio::sync::Semaphore` 控制并发数 + `futures::stream::StreamExt` 的 `buffer_unordered` |
| 错误处理 | 自定义 `enum UploadError`，配合 `thiserror` crate 派生 `Error` trait，替代 JS 的 try/catch |
| 重试逻辑 | 自行实现指数退避重试，或使用 `backoff` crate |
| 进度回调（上传进度条） | Tauri 的 `Window::emit` 将进度事件发送回前端，替代原本 JS 侧直接更新 UI 的方式 |

## 4. 迁移步骤

### 4.1 前置调研（每个文件迁移前都要做）

- [ ] 通读该 JS 文件，列出所有外部依赖（npm 包）及其用途
- [ ] 标记所有 Node 特有 API 调用（`fs`、`crypto`、`stream` 等）
- [ ] 确认该文件是否有单元测试或可复用的测试用例，没有的话先补一份最小验证用例（哪怕是手动测试步骤清单），作为迁移前后行为对照的基准

### 4.2 逐文件迁移

对每个文件建立独立的迁移检查项：

- [ ] 文件 1：`____`（文件名待补充）— 功能：`____`
- [ ] 文件 2：`____` — 功能：`____`
- [ ] 文件 3：`____` — 功能：`____`
- [ ] 文件 4：`____` — 功能：`____`
- [ ] 文件 5：`____` — 功能：`____`
- [ ] 文件 6（如有）：`____` — 功能：`____`

> 建议在实际开始迁移时，把这 5-6 个文件的真实名称和职责填进上表，作为迁移进度追踪表。

每个文件的迁移动作：

1. 在 Rust 侧新建对应模块（如 `src-tauri/src/upload/xxx.rs`）
2. 按第 3 节对照表替换对应能力
3. 暴露为 Tauri command（`#[tauri::command]`），保持与原 JS 侧被调用时一致的参数/返回结构
4. 编写该模块的 Rust 单元测试（至少覆盖：正常上传成功、网络失败重试、文件不存在/权限错误三种场景）
5. 前端调用点从"调用 sidecar 进程"改为直接 `invoke('command_name', args)`
6. 手动测试该功能点（对照 4.1 中的基准用例）通过后，再进行下一个文件

### 4.3 并发/队列逻辑的重点验证场景

上传功能常见的坑集中在并发处理上，迁移后需要专门验证：

- 多文件同时选择上传时，并发数控制是否生效（不应该无限并发打满带宽/触发服务端限流）
- 单个文件上传失败时，是否影响队列中其他文件的正常上传
- 大文件（建议测试 ≥100MB）上传是否为流式读取，而不是一次性读入内存
- 上传过程中取消操作（如果原功能支持）是否能正确中断请求并清理资源

### 4.4 清理阶段

全部文件迁移验证通过后：

- [ ] 删除原 JS 上传逻辑源文件
- [ ] 移除 `package.json` 中仅供上传逻辑使用、迁移后不再需要的 npm 依赖
- [ ] 移除 `tauri.conf.json` 中 `bundle.externalBin` 里指向 Node sidecar 二进制的配置
- [ ] 移除 CI/CD workflow 中构建 Node sidecar 二进制的步骤（对应项目 spec 第 5.1 节遗留的待办）
- [ ] 全平台（Windows/macOS/Linux）分别打包验证一次上传功能完整可用

## 5. 风险与回滚策略

- 迁移期间建议用独立分支进行，每个文件迁移完成、验证通过后再合并，避免主分支长期处于"半 JS 半 Rust"不可用状态
- 如果某个文件迁移后出现难以定位的行为差异（尤其是哈希算法、编码格式相关的细节问题），保留原 JS 文件作为参照对比，不要在没有基准对照的情况下直接删除
- 建议迁移完成后有一个观察期（比如自己日常使用几天），再彻底移除 Node.js 相关配置和依赖
